# 部署指南

> 面向自托管用户：从零启动、Docker 部署、环境变量、持久化与升级。

## 1. 前置条件

| 组件 | 要求 |
|------|------|
| Node.js | ≥ 22（`engines` 已声明） |
| Chromium | `npx playwright install chromium`；有本机 Chrome 151+ 也可 |
| Linux 无头服务器 | 安装 Xvfb，用 `xvfb-run -a` 启动 |
| Python | 仅部署校验脚本需要（可选） |

运行时依赖只有 `patchright` / `playwright` / `undici`，`npm install` 即可，无需编译原生模块。Rust 加速模块是可选优化，不构建时自动走 JS 实现，行为一致。

## 2. 源码运行

```bash
git clone https://github.com/xiaoli0412/sakana2api.git
cd sakana2api
npm install
npx playwright install chromium

node server.js          # 有图形环境
xvfb-run -a node server.js   # 无头 Linux
```

默认监听 `0.0.0.0:8787`。浏览器打开 `http://127.0.0.1:8787/` 进入管理面板；首次启动会自动获取会话，日志出现 `Session ready` 即就绪。

## 3. Docker Compose

```bash
docker compose up -d
```

- 持久化状态挂载在 `./runtime`，升级镜像不丢会话、账号池、密钥与审计。
- 容器内已包含 Chromium 与运行依赖；无头环境由 entrypoint 处理。
- 需要外网访问时在反向代理上传 TLS，服务本身只提供 HTTP。

## 4. 关键环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `PORT` / `HOST` | `8787` / `0.0.0.0` | 监听地址 |
| `API_KEY` | – | 静态业务密钥；设置后 `/v1/*` 需带此密钥 |
| `ADMIN_API_KEY` | – | 管理员密钥；管理端点只认它 |
| `AUTO_SESSION` | `true` | `false` 时不启动浏览器、不自动补号，只用 `SAKANA_SESSION_FILE` |
| `ACCOUNT_POOL_MIN` / `ACCOUNT_POOL_MAX` | `50` / `50` | 账号池目标与上限 |
| `MAX_CONCURRENT_PER_ACCOUNT` | `6` | 单账号并发上限 |
| `REQUEST_TIMEOUT_MS` | `300000` | 单请求超时 |
| `CACHE_ENABLED` | `false` | 响应缓存（默认关闭） |
| `CONTEXT_COMPACT_THRESHOLD_BYTES` | `0` | 上游压缩阈值，0 表示关闭 |
| `WRITER_COMPACT_THRESHOLD_BYTES` | `0` | 写作模型压缩阈值，0 表示关闭 |
| `OPTICAL_CONTEXT_THRESHOLD` | `200000` | 光学压缩触发字节数；`OPTICAL_CONTEXT=0` 关闭 |
| `SAKANA_BASE` | 上游官方地址 | 仅测试或镜像环境修改 |
| `SAKANA_MINI_UPSTREAM` / `SAKANA_CODE_UPSTREAM` | 上游默认 | 上游改名时的热修开关 |

完整清单见 [README](https://github.com/xiaoli0412/sakana2api#readme)。

## 5. 鉴权三态

| 状态 | 触发条件 | 行为 |
|------|----------|------|
| 开放模式 | 无 `API_KEY`、无 `ADMIN_API_KEY`、无业务 Key | 全部接口免鉴权，仅建议本机使用 |
| Key 模式 | 存在业务 Key 或管理员密钥 | `/v1/*` 需有效业务/管理员密钥 |
| 管理锁 | 配置了 `ADMIN_API_KEY`（或持久化 `runtime/admin_key`） | 管理端点仅管理员密钥 |

业务密钥以 sha256 哈希存储。撤销全部业务 Key 不会在管理员密钥仍存在时把服务退回开放模式。

## 6. 状态与持久化

- `session.json`、`account_pool.json`、`keys.json`、审计日志、邮箱配置都写入 `runtime/`，再符号链接进程序目录。
- 部署脚本对持久化数据做失败即停止的迁移预检；同名冲突会保留双方等待人工处理。
- 不要把 `runtime/` 提交到 Git；其中包含会话 cookie。

## 7. 升级注意

- **v0.21.0 行为变更**：显式 `conversation_id` 默认不再按 delta 续聊，默认 full；依赖旧语义的客户端需显式 `history_mode: "delta"`。
- 升级后先看 `/health` 与面板账号池；上游政策变化（Turnstile、注册封锁、模型改名）可能影响自动补号。
- 2026-10 起自动注册链路不可依赖，补号请走[账号池运维](账号池运维)中的人工导入。

## 8. 排障速查

| 症状 | 处理 |
|------|------|
| `EADDRINUSE` | 端口被占用，清理残留进程或改 `PORT` |
| 浏览器启动失败 | `npx playwright install chromium`，无头环境检查 Xvfb |
| `/health` 正常但对话 401 | 检查 `API_KEY` 与请求头 `Authorization: Bearer …` |
| 账号池不增长 | 上游封锁期属预期，按人工导入流程补号 |
| 大量 403 / 过盾失败 | 降低补号与探测频率，检查出口 IP 是否被重点挑战 |

## 9. 机房 IP 被 Cloudflare 拦截时的代理出口

**症状**：`/health` 和模型列表正常，但 `/v1/chat/completions` 返回 `403 FORBIDDEN`；服务器上的 Chromium 打开 chat.sakana.ai 也停在 403。这是出口 IP 被站点 WAF 拦截，不是账号被封。

**处理**：

1. 在服务器本地运行 mihomo/clash，只监听 `127.0.0.1`，选一个浏览器能正常打开 chat.sakana.ai 的节点；
2. 让浏览器与 Node 请求走同一个出口：

   ```bash
   export SAKANA_BROWSER_PROXY=http://127.0.0.1:7992
   export SAKANA_UPSTREAM_PROXY=http://127.0.0.1:7992
   export SAKANA_BROWSER_HEADLESS=1   # 无 X/Xvfb 的服务器必须开
   ```

3. 两者必须指向同一出口：`cf_clearance` 绑定 IP，浏览器走一个出口、Node 走另一个会重新 403；
4. 重启服务后先验证 `curl -x http://127.0.0.1:7992 https://chat.sakana.ai/api/v2/user/settings` 返回 401（表示已过 CF），再由自动补池注册账号。

systemd 单元示例（配置里的节点信息不要提交到 Git）：

```ini
[Unit]
Description=Sakana egress proxy (mihomo)
After=network-online.target

[Service]
ExecStart=/usr/local/bin/mihomo -d /root/sakana-2api.runtime/mihomo -f /root/sakana-2api.runtime/mihomo/config.yaml
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

## 10. 自检

```bash
npm test            # 全量串行（44 个 node 测试 + 1 个部署校验）
npm run test:core   # 无端口纯逻辑组
npm run test:http   # HTTP / 浏览器组
npm run test:native # 原生模块契约
npm run test:deploy # 部署运行时配置
```

HTTP 组内测试绑定本机端口、共享运行时状态，按设计**串行执行**；不要并行跑同一组测试，否则会出现端口冲突与状态互踩。
