# 账号池运维

> 账号池如何调度、如何人工补号、导入校验看什么、2026-10 上游封锁期的最佳实践。

## 1. 池子里的东西

| 概念 | 说明 |
|------|------|
| 活跃账号 | `state=active`，可被租约选中；每账号默认最多 6 并发 |
| 限流 | `state=rate_limited`，命中上游配额后进入冷却（`RATE_LIMIT_COOLDOWN_MS`，默认 10 分钟） |
| 过期 | `state=expired`，会话被上游判定失效；留作墓碑便于诊断 |
| 租约 | 每次请求租一个账号，结束释放；`leaseCount` / `inFlight` / `stale` 可在面板看到 |
| 补号 | 活跃数低于 `ACCOUNT_POOL_MIN` 时自动补充，目标与上限见 `ACCOUNT_POOL_MAX` |
| 陈旧 | 账号超过 `ACCOUNT_STALE_MS`（默认 15 分钟）未刷新会标记 stale 并优先刷新 |

账号池只保存服务端会话；面板与 `/api/accounts` 只返回安全字段（Cookie 数量、状态、错误分类、租约年龄等），cookie 与 token 永不出服务端。

## 2. 2026-10 的现实：人工导入是第一路径

上游加入 Cloudflare Turnstile 会话闸门并封锁一次性邮箱注册，自动注册链路不可依赖。补号流程：

1. 在自己的真实浏览器登录 `https://chat.sakana.ai`；
2. 从浏览器扩展或 DevTools 复制 Cookie（必须包含 `sakana-chat`）；
3. 管理面板「账号池 → 导入人工登录会话」粘贴，点「校验并导入」；
4. 服务端先请求上游 `/api/v2/user/settings` 验证会话，再读取 `/api/rate-limit/status` 配额快照；
5. 校验通过才入池；失败直接拒绝，不占用池位。

命令行等价：

```bash
curl -X POST http://127.0.0.1:8787/api/accounts/import \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H "content-type: application/json" \
  -d '{"cookieHeader":"sakana-chat=<值>; cf_clearance=<值>"}'
```

## 3. 支持的导入格式

| 来源 | 形态 |
|------|------|
| 原始 Cookie 头 | `a=b; c=d`，可带 `Cookie:` 前缀（curl 复制） |
| Cookie-Editor / EditThisCookie | JSON 数组：`[{"name","value","domain","path"}]` |
| Playwright storageState | `{"cookies":[...],"origins":[]}` |
| curl / yt-dlp cookie jar | `cookies.txt`（Netscape 7 列格式） |
| 结构化 API | `{"cookies":[{"name","value"}]}` |

面板会自动识别格式；服务端做权威解析。非 `sakana.ai` 域的 cookie 会被丢弃，含 CRLF 的输入直接拒绝。

## 4. 校验结果怎么看

成功响应：

```json
{
  "ok": true,
  "id": "…",
  "poolSize": 51,
  "validation": {
    "status": "active | quota_exhausted",
    "format": "header | json | cookies.txt | cookies",
    "cookieCount": 2,
    "upstreamStatus": 200,
    "quota": { "ok": true, "models": [{ "id": "sakana-namazu", "exceeded": false }], "exceeded": [] }
  }
}
```

失败响应保留既有错误码，并补充 `reason`：

| code | reason | 含义 | 处理 |
|------|--------|------|------|
| `INVALID-SESSION` | – | 格式错误 / 缺 `sakana-chat` / 控制字符 | 重新导出 Cookie |
| `SESSION-REJECTED` | `invalid_session` | 上游 401，会话已失效 | 重新登录后导出 |
| `SESSION-REJECTED` | `turnstile_challenge` | 403 过盾失败 | 换出口 IP / 稍后重试，勿连续猛探 |
| `SESSION-REJECTED` | `rate_limited` | 上游 429 | 按 `retryAfterMs` 等待 |
| `SESSION-REJECTED` | `upstream_error` / `network_error` | 上游 5xx 或网络失败 | 稍后重试 |
| `DUPLICATE-SESSION` | – | 会话已在池中或已隔离 | 无需重复导入 |
| `PROBE-BACKOFF` | `backoff` / `throttled` | 连续系统性失败后的探测退避 | 等 `retryAfterMs` 再试 |

`/api/accounts` 额外返回 `validations`（按账号 ID 的最近一次导入校验）、`leaseCount`、`inFlight`、`stale` 与 `importProbe`，面板据此显示"活 / 配额耗尽 / 未校验"。

## 5. 探测预算与热修开关

反复探测会加重 Turnstile 挑战，因此导入探测自带窗口限流与指数退避（只对系统性失败计数：过盾、限流、5xx、网络；401 视为明确答案，不触发退避）。

| 变量 | 默认 | 说明 |
|------|------|------|
| `SAKANA_IMPORT_PROBE_FAIL_THRESHOLD` | `3` | 连续多少次系统性失败后开始退避 |
| `SAKANA_IMPORT_PROBE_BACKOFF_MS` | `2000` | 退避基数，按次数指数增长 |
| `SAKANA_IMPORT_PROBE_BACKOFF_MAX_MS` | `60000` | 退避上限 |
| `SAKANA_IMPORT_PROBE_WINDOW_MS` | `60000` | 探测窗口长度 |
| `SAKANA_IMPORT_PROBE_MAX_PER_WINDOW` | `20` | 窗口内最多探测次数 |
| `SAKANA_IMPORT_PROBE_TIMEOUT_MS` | `15000` | 会话探测超时 |
| `SAKANA_IMPORT_QUOTA_PROBE` | `1` | 设 `0` 关闭配额快照请求 |
| `SAKANA_IMPORT_QUOTA_TIMEOUT_MS` | `10000` | 配额请求超时 |

上游行为变化时优先用这些变量热调，不必改代码发版。

## 6. 日常运维

- **补号**：面板「触发补号」或 `POST /api/accounts/refresh`；封锁期以人工导入为主。
- **观察**：面板账号池页看活跃/限流/过期、租约与最近校验；`/api/stats` 的 `accounts` 段给脚本用。
- **清理**：失效账号保留 `ACCOUNT_TOMBSTONE_TTL_MS`（默认 24h）后由池压缩移除；正在租用的账号不会被删。
- **关闭自动链路**：`AUTO_SESSION=false` 时只使用 `SAKANA_SESSION_FILE` 的显式会话，不启动浏览器、不补号、不刷新旧池。
- **安全**：不要把 `account_pool.json` / `session.json` / `runtime/` 提交或分享；导入接口只接受管理员密钥，响应永不回显 cookie。
