# 会话与隔离详解

> v0.21.0 起的显式 full/delta 契约：什么时候新建会话、什么时候续聊、多人共用一把 Key 为何不串线。

## 1. 两种模式

| 模式 | 触发 | 行为 |
|------|------|------|
| `full`（默认） | 不传 `history_mode` 或传 `full` | 每次都按客户端提供的完整历史建立独立上游会话；无状态、可重放 |
| `delta`（显式） | `history_mode: "delta"` + `conversation_id` | 只发送最新一轮，在该 ID 上继续；同会话请求串行化 |

v0.21.0 之前"带 `conversation_id` 就默认 delta"的隐式行为已移除。老客户端如果依赖它自动续聊，需要显式声明 `history_mode`；否则会按 full 重建上下文。

## 2. 为什么默认 full

- 不依赖服务端记忆：进程重启、账号轮换、上游会话过期都不会造成静默丢历史。
- 更适合多用户共享同一把 Key：每个请求的历史由客户端自己携带，天然互不污染。
- 上游会话是有状态资源；默认 full 把"是否复用"的决定权交给调用方。

## 3. delta 的归属与隔离

每个 upstream 会话记录 `conversationId`、所属凭据、账号亲和与模型。续聊时必须同时满足：

1. 当前凭据拥有该会话（跨 Key 复制 ID → 409 拒绝）；
2. 浏览器范围标识匹配：面板会自动附加 `x-client-session-id`，同 Key 多用户各用各的范围；
3. 模型一致（不一致 → `CONTEXT_MODEL_MISMATCH`，提示新建会话）。

跨凭据访问返回 409，不会"借用"别人的会话，也不会静默切换账号。

## 4. 错误语义（绝不静默丢上下文）

| code | 触发 | 客户端动作 |
|------|------|------------|
| `CONTEXT_ID_REQUIRED` | delta 没带 `conversation_id` | 补 ID，或改回 full |
| `CONTEXT_ID_INVALID` | ID 格式非法 | 使用服务返回的 `x-conversation-id` |
| `CONTEXT_EXPIRED` | 会话超过 24h TTL 或上游已失效 | 重发完整历史（含原始附件）新建会话 |
| `CONTEXT_MODEL_MISMATCH` | 续聊模型与建会话时不一致 | 新建会话，或回到原模型 |
| `CONTEXT-AFFINITY-MISSING` | 会话所属账号不可用 | 重发完整历史；不要盲目重试 |

代理不会用"只补最后一轮"的方式假装恢复；客户端应保留原始附件，便于 full 重放。

## 5. 并发与串行化

- 同一 `conversation_id` 的 delta 请求串行执行，避免上游消息树交错；不同会话并行。
- 每个账号默认最多 6 个并发租约（`MAX_CONCURRENT_PER_ACCOUNT`），排队时响应会先发 SSE 心跳避免客户端超时。
- 客户端断开或超时会取消上游请求并释放租约；停止按钮走 `POST /v1/conversations/{id}/stop`。
- 会话状态有 24h TTL，过期条目会被清理；过期不等于错误，full 请求不受影响。

## 6. 上下文计量

`usage` 统计组装后的完整输入：系统注入、全部附件文本、光学压缩页按像素折算、搜索轮独立计入。流式响应在尾 chunk 汇总，UI 显示 tok/s。所有数值都是启发式估算，响应带 `x-usage-estimated: true` 标识；不要把它当作上游权威账单。

## 7. 实践建议

- 共享 Key 的群聊场景：默认 full，各自携带历史；或给每个用户独立的 `x-client-session-id`。
- 长对话客户端：保存 `x-conversation-id`，下一轮用 `history_mode: "delta"`；收到 409 时回退 full 重放。
- 切换模型：不要复用旧 `conversation_id`，先新建会话再续聊。
- 审计排障：管理面板的审计日志只记录元数据（路径、模型、状态、耗时、字节数），不落 cookie、正文与提示词。
